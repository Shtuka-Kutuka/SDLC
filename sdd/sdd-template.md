## 1. Введение

### 1.1 Назначение документа

SDD описывает проектное решение для desktop-приложения GameShelf и переводит согласованные требования SRS в архитектурные представления, достаточные для реализации. Документ предназначен для архитектора, Java-разработчиков, тестировщиков и сопровождающих специалистов и используется при реализации, проверке архитектурных ограничений и анализе изменений.

### 1.2 Область применения

GameShelf 0.1 предназначен для просмотра каталога настольных игр, поиска, фильтрации, просмотра подробной информации, выставления оценок и публикации отзывов. Зарегистрированные пользователи управляют избранным и личными коллекциями, администратор управляет карточками игр. После второго раунда добавлена функция сравнения 2–3 игр по ключевым характеристикам. Онлайн-покупки, игровые сессии, чат, мобильный и веб-клиенты, внешние API и ИИ/МО остаются вне релиза.

## 2. Обзор дизайна

### 2.1 Задачи стейкхолдеров

| Стейкхолдер | Интересы | Архитектурный ответ |
|---|---|---|
| Пользователь | Понятная навигация, быстрый поиск, сохранность коллекций | UI, сценарии взаимодействия, модель данных |
| Администратор | Корректность каталога, ограничение доступа | GameService, роли и проверки полномочий |
| Заказчик | Сроки, бюджет, соответствие ожиданиям | Декомпозиция требований, итерационный план, ADR |
| Разработчик | Модульность и тестируемость | Три слоя, интерфейсы сервисов и репозиториев |
| Тестировщик | Проверяемые критерии | Трассировка требований и тестовые сценарии |
| Сопровождение | Диагностика ошибок | Логирование и обработка исключений |

### 2.2 Выбранные точки зрения

Используются контекстная, композиционная, логическая, информационная, интерфейсная, интеракционная, алгоритмическая и deployment-точки зрения. Физическая инфраструктура ограничивается компьютером пользователя и доступным экземпляром PostgreSQL.

#### 2.2.1 Контекст

Акторы: Гость, Авторизованный пользователь, Администратор. Внешняя зависимость — PostgreSQL. Граница системы — JavaFX desktop-приложение и его слой доступа к БД. Прямые интеграции со сторонними сервисами не входят в релиз.

#### 2.2.2 Композиция

Система разделена на три слоя:
1. **Presentation Layer:** JavaFX-экраны, контроллеры, модели отображения и проверка пользовательского ввода.
2. **Business Logic Layer:** сервисы каталога, поиска, рейтингов, отзывов, пользователей, коллекций, сравнения и администрирования.
3. **Data Access Layer:** репозитории/DAO, маппинг сущностей и транзакции JDBC или JPA.

Направление вызовов: UI → Service → Repository → PostgreSQL. DAL не обращается к UI.

#### 2.2.3 Логическое представление

Основные сущности: `User` (логин, хеш пароля, роль), `Game` (название, описание, жанр, число игроков, длительность, возрастное ограничение), `Rating`, `Review`, `Favorite`, `Collection`, `CollectionGame`. Основные сервисы: `UserService`, `GameService`, `RatingService`, `ReviewService`, `CollectionService`, `ComparisonService`, `AdminService`. Репозитории: `UserRepository`, `GameRepository`, `RatingRepository`, `ReviewRepository`, `CollectionRepository`.

Оценка и отзыв принадлежат конкретному пользователю и игре. Коллекция принадлежит пользователю и содержит связи с играми.

#### 2.2.4 Физическое представление

Персональный компьютер с поддерживаемой ОС и установленной Java/JavaFX. PostgreSQL доступен локально либо по сети. Приложение использует конфигурационные параметры подключения. Минимальные CPU/RAM и целевые версии ОС фиксируются после выбора целевой платформы и проверки сборки.

#### 2.2.5 Структура

```text
gameshelf/
  app/                 # запуск и конфигурация
  presentation/        # JavaFX views, controllers, view models
  service/             # auth, catalog, rating, review, collection, comparison, admin
  domain/              # сущности и доменные исключения
  data/                # repositories, mappers, transactions
  security/            # хеширование и авторизация
  logging/             # журналирование
```

Контроллеры не содержат SQL и бизнес-правила; репозитории не управляют элементами интерфейса.

#### 2.2.6 Зависимости

`presentation` зависит от `service`; `service` — от доменных сущностей и абстракций репозиториев; `data` реализует репозитории и зависит от JDBC/JPA и PostgreSQL. `security` предоставляет хеширование и проверку ролей. `logging` используется всеми слоями.

#### 2.2.7 Информация

Предварительные таблицы: `users`, `games`, `ratings`, `reviews`, `favorites`, `collections`, `collection_games`. Используются PK/FK, ограничения уникальности для пользовательских оценок и избранного, ограничения допустимого диапазона оценки. Пароль хранится только как стойкий хеш. Схема уточняется и фиксируется миграциями.

#### 2.2.8 Интерфейс

Экраны: главное окно, каталог, поиск/фильтры/сортировка, карточка игры, регистрация/авторизация, избранное, коллекции, формы оценки/отзыва, административная форма игры и экран сравнения. UI показывает сообщения о неверном вводе, отказе в доступе и недоступности БД.

#### 2.2.9 Взаимодействие

**Поиск:** ввод запроса → проверка ввода контроллером → `GameService` формирует критерии → репозиторий выполняет параметризованный запрос → результат отображается. Пустой результат сопровождается соответствующим состоянием UI.

**Оценка:** пользователь выбирает оценку → `RatingService` проверяет авторизацию, игру и диапазон → репозиторий сохраняет/обновляет запись → UI обновляет рейтинг. Неавторизованная операция отклоняется.

**Ошибка БД:** репозиторий получает ошибку → она преобразуется в прикладное исключение → UI показывает безопасное сообщение, технические сведения записываются в журнал.

#### 2.2.10 Алгоритм

Поиск и фильтрация выполняются параметризованными запросами PostgreSQL. Сортировка разрешена только по заранее определённым полям рейтинга и популярности. Рейтинг рассчитывается как агрегат пользовательских оценок; при отсутствии оценок показывается «нет оценок». Сравнение формирует таблицу атрибутов 2–3 игр и выделяет отличающиеся значения.

#### 2.2.11 Динамика состояний

Состояния сессии: `Guest` → `Authenticated` после успешного входа; `Authenticated` → `Guest` после выхода. Роль `ADMIN` разрешает административные операции, `USER` — нет. При ошибке входа состояние не меняется. Недоступность БД не должна приводить к аварийному завершению приложения.

#### 2.2.12 Параллелизм

JavaFX UI обновляется в JavaFX Application Thread. Потенциально длительные запросы выполняются вне UI-потока, результат возвращается в UI-поток. Одновременное изменение данных контролируется транзакциями и ограничениями БД.

#### 2.2.13 Паттерны

MVC-подобное разделение JavaFX-представления и контроллеров; Service Layer; Repository/DAO; DTO/ViewModel. DI-фреймворк допустим, но не обязателен.

#### 2.2.14 Развёртывание

Поставка — исполняемый Java-артефакт или пакет для целевой ОС. PostgreSQL развёртывается отдельно или локально. Параметры подключения не зашиваются в исходный код. Изменения проходят Pull Request и code review.

#### 2.2.15 Ресурсы

Для каталога рекомендуется пагинация. Индексы по названию и внешним ключам добавляются после проверки запросов. Длительные операции не блокируют UI. Целевой ориентир SRS REQ-PERF-001 — не более 3 секунд для основных операций при нормальной нагрузке и доступной БД.

## 3. Проектные представления

### DV-01 — Трёхслойная архитектура
- **Viewpoint:** Composition / Dependency.
- **Representation:** UI вызывает сервисы; сервисы используют интерфейсы репозиториев; репозитории взаимодействуют с PostgreSQL.
- **Требования:** REQ-FUNC-001…010, REQ-REL-001, REQ-OBS-001.
- **Решение:** ADR-001.

### DV-02 — Учётные записи и доступ
- **Viewpoint:** Logical / State Dynamics / Interaction.
- **Representation:** `UserService` выполняет регистрацию и вход; `PasswordHasher` сохраняет и проверяет хеш; `AuthorizationService` проверяет роль.
- **Требования:** REQ-FUNC-007, REQ-SEC-001, REQ-SEC-002.
- **Решение:** ADR-002.

### DV-03 — Хранение данных
- **Viewpoint:** Information.
- **Representation:** реляционная схема PostgreSQL, внешние ключи, уникальные ограничения и транзакции.
- **Требования:** REQ-FUNC-001…010, REQ-REL-001.
- **Решение:** ADR-003.

### DV-04 — Поиск и сортировка
- **Viewpoint:** Algorithm / Interface.
- **Representation:** единый объект критериев, фильтры жанра/числа игроков/рейтинга, белый список сортировки.
- **Требования:** REQ-FUNC-002, 003, 009, REQ-PERF-001.
- **Решения:** ADR-001, ADR-003.

### DV-05 — Оценки, отзывы и коллекции
- **Viewpoint:** Logical / Interaction / Information.
- **Representation:** операции доступны после авторизации; записи связаны с пользователем и игрой; ограничения БД предотвращают дублирование.
- **Требования:** REQ-FUNC-005, 006, 008.
- **Решения:** ADR-002, ADR-003.

### DV-06 — Сравнение игр
- **Viewpoint:** Interface / Algorithm.
- **Representation:** пользователь выбирает 2–3 игры; `ComparisonService` получает характеристики и формирует таблицу; сравнение не изменяет каталог.
- **Требования:** SYS-CMP-01…03.
- **Решение:** ADR-004.

### DV-07 — Ошибки и журналирование
- **Viewpoint:** Interaction / Resources.
- **Representation:** преобразование инфраструктурных ошибок в прикладные исключения; запись времени, компонента и типа ошибки без секретов.
- **Требования:** REQ-REL-001, REQ-OBS-001.
- **Решения:** ADR-001, ADR-003.

## 4. Решения

| ID | Решение | Статус | Обоснование |
|---|---|---|---|
| ADR-001 | Трёхслойная архитектура JavaFX / Service / DAL | Accepted | Соответствует SRS, обеспечивает разделение ответственности |
| ADR-002 | Хеширование паролей и ролевая авторизация | Accepted | Необходимо для REQ-SEC-001/002 |
| ADR-003 | PostgreSQL и Repository/DAO через JDBC или JPA | Accepted | Соответствует SRS и обеспечивает целостность |
| ADR-004 | Сравнение игр отдельным внутренним сервисом | Proposed | Добавлено после второго раунда, без внешних API |
